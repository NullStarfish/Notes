# Broadcast Core Array 与 Systolic Array

> [!question] 从 PE Array 到整个 Tile Compute Core Array，一个 GEMM 究竟怎样被计算？
> [[Matrix Engine]] 讨论过标量 MAC、二维 PE 与 skew；[[Tiling]] 讨论了驻留、复用和容量。这里进一步区分阵列的**计算粒度、空间分工、归约过程和通信方式**，理解 broadcast core array 与 systolic array 的关系。

本文先让 GEMM 的输出区域能映射到一个阵列，避免把外层多轮输出分块与阵列内部执行混在一起。模型中的周期数均会单独说明假设。

## 1. 先分开两个问题：计算粒度与通信方式

讨论中最容易混淆的是：我们常拿“标量 MAC 构成的 systolic array”，对比“能运行矩阵 kernel 的独立 core array”，同时改变了两个设计维度。

| 设计维度 | 需要回答的问题 | 可选方式 |
| --- | --- | --- |
| 计算粒度 | 一个位置负责什么输出、执行什么操作？ | 一个输出标量与 MAC；一个输出 Tile 与矩阵 kernel |
| 通信方式 | 输入怎样到达各个计算位置？ | 邻居逐级转发；上游存储与网络分发 |

因此可以设计标量广播阵列，也可以设计由矩阵 core 组成的 block-systolic 阵列。一个 core 内部甚至可以包含小型 systolic array，而 core 之间使用广播。

**数学上的分块方式可以相同，数据分发方式却不同；通信拓扑也不能单独决定每个计算位置内部的实现。**

## 2. 标量 Output-Stationary Systolic Array 在做什么？

先限定为经典二维 output-stationary 模型：有 $R$ 行、$S$ 列标量 PE，每个 PE 每周期可执行一次 MAC，负责一个 $c_{ij}$：

$$
C_{R\times S}=A_{R\times K}B_{K\times S},
\qquad c_{ij}\mathrel{+}=a_{ik}b_{kj}.
$$

M、N 两个输出方向映射到 PE 的行、列；K 方向逐项在时间上执行。A 从左向右传，B 从上向下传，部分和保留在负责该输出的 PE 中。

> [!question] Systolic 只是数据流过 PE，并没有显式地把 A 切成行 Tile、B 切成列 Tile。它也在完整 K 上归约吗？

是的。固定 PE$(i,j)$ 后，它最终要计算：

$$
c_{ij}=a_{i0}b_{0j}+a_{i1}b_{1j}+\cdots+a_{i,K-1}b_{K-1,j}.
$$

每个有效周期只执行其中一项，但最终仍完成全部 K 项。Skew 改变各 PE 的开始时刻，没有改变求和范围。

从数学上，固定一个 k 的所有乘积构成一次外积：

$$
C\mathrel{+}=A[:,k]B[k,:].
$$

但在 systolic 中，这个外积的不同位置并不在同一个物理周期完成，而是沿波前展开。若把每个 PE 看成一个最小输出块，可用 $B_M=B_N=B_K=1$ 描述这层逻辑更新；这不代表外部存储只能按单元素搬运。

当实际 M、N 大于物理阵列覆盖范围，仍然需要外层 tiling。数据以流的形式到达，不代表矩阵在逻辑上没有分块。

## 3. 把一个标量 PE 换成能算矩阵的 Core

现在设阵列有 $P_M$ 行、$P_N$ 列 core。每个 core 负责一个 $B_M\times B_N$ 的输出 Tile，而不是一个标量。它每轮接收 A/B 子块，执行一次逻辑上的 block GEMM 更新：

$$
C_{i,j}\mathrel{+}=A_{i,q}B_{q,j}.
$$

这里 i、j 是输出块索引，q 是 K 方向的块索引。**一次 block GEMM 是多条指令、多次 MAC 的计算任务，不是默认一个周期做完。**

### 3.1 “你分发的 A₀ 到底是什么？为什么只有一个下标？”

> [!question] 标量 systolic 传的是小元素。讨论里写的 $A_0$ 是一行、一列，还是矩阵块？只有一个下标，K 方向的位置去哪里了？

单写 $A_0$ 省略了 K 方向的块索引，会混淆“完整行带”与“当前归约子块”。这里始终保留两个块下标：

$$
\begin{aligned}
A_{i,q}&=A[iB_M:(i+1)B_M,\ qB_K:(q+1)B_K],\\
B_{q,j}&=B[qB_K:(q+1)B_K,\ jB_N:(j+1)B_N].
\end{aligned}
$$

于是：

$$
A_{i,q}\in\mathbb{R}^{B_M\times B_K},\quad
B_{q,j}\in\mathbb{R}^{B_K\times B_N},\quad
C_{i,j}\in\mathbb{R}^{B_M\times B_N}.
$$

两个块下标描述它在大矩阵中的位置；每块内部仍有行、列两个元素索引。与之相对，$A_{i,:}$ 表示跨全部 K 块的完整行带，形状是 $B_M\times K$。

### 3.2 一个 $2\times3$ Core Array 的完整例子

计算 $A_{8\times16}B_{16\times12}=C_{8\times12}$，单核 $B_M=4,B_N=4,B_K=8$。A 分成 $2\times2$ 块，B 分成 $2\times3$ 块：

$$
A=\begin{bmatrix}A_{0,0}&A_{0,1}\\A_{1,0}&A_{1,1}\end{bmatrix},
\qquad
B=\begin{bmatrix}B_{0,0}&B_{0,1}&B_{0,2}\\B_{1,0}&B_{1,1}&B_{1,2}\end{bmatrix}.
$$

每块 A 为 $4\times8$，每块 B 为 $8\times4$。输出分给六个 core：

|  | 第 0 列 | 第 1 列 | 第 2 列 |
| --- | --- | --- | --- |
| 第 0 行 | $C_{0,0}$ | $C_{0,1}$ | $C_{0,2}$ |
| 第 1 行 | $C_{1,0}$ | $C_{1,1}$ | $C_{1,2}$ |

以 core$(0,1)$ 为例：

$$
C_{0,1}=A_{0,0}B_{0,1}+A_{0,1}B_{1,1}.
$$

两个 K 轮的输入需求分别是：

| 归约轮 | 向第 0 行共享 | 向第 1 行共享 | 向第 j 列共享 |
| --- | --- | --- | --- |
| $q=0$ | $A_{0,0}$ | $A_{1,0}$ | $B_{0,j}$ |
| $q=1$ | $A_{0,1}$ | $A_{1,1}$ | $B_{1,j}$ |

这样写，数据块的空间归属与归约轮次就都明确了。

### 3.3 “沿整个 K 归约”没有取消 $B_K$

> [!question] Core Array 沿完整 K 归约，好像不再在 $B_K$ 上归约，也不再设置 stationary tile？

这里要区分**一次更新覆盖的长度**与**输出保留的完整生命周期**。上述例子中，每轮 block GEMM 处理 8 个 k；做两轮后，C 才完成全部 16 项归约：

$$
C_{i,j}=\sum_{q=0}^{K/B_K-1}A_{i,q}B_{q,j}.
$$

C Tile 跨全部 q 保留，正是 output stationary。A/B 仍然可以按 $B_K$ 分批送入，不需要把整个 $B_M\times K$ 的 A 行带和 $K\times B_N$ 的 B 列带同时装进 core。

因此：**K 决定归约什么时候结束；$B_K$ 决定每批输入与局部计算的大小；C 的驻留范围可以跨越所有这些批次。**尺寸不能整除时，最后一批需要相应的尾部处理。

## 4. Broadcast + Independent Core 怎样工作？

### 4.1 独立执行，不代表没有共享与同步

采用前面的输出划分，上游缓冲与分发网络把 $A_{i,q}$ 送给第 i 行的多个 core，把 $B_{q,j}$ 送给第 j 列的多个 core。每个 core 维护自己的 C，只完成自己负责的输出：

```python
# core(i, j) 的逻辑工作；receive 表示数据就绪与取得使用权
C_local = zeros(BM, BN)
for q in range(K_tiles):
    A_local = receive_A(i, q)
    B_local = receive_B(q, j)
    C_local += local_gemm(A_local, B_local)
    release_inputs(q)
write_output(i, j, C_local)
```

独立指不需要把某个 core 算出的 C 部分和交给另一个 core 来完成同一输出，也不要求计算 core 先消费输入、再向邻居转发。仍然需要协调输入就绪、缓冲复用、共享传输和最终输出；不同 core 的速度差异也可能通过共享队列或背压互相影响。

这类映射的一个具体实例是讨论中的 Ryzen AI NPU 论文：§4.2.1 将 M/N 映射到空间、K 留在时间上；A 按行、B 按列广播，C 保留在每核 L1，局部 kernel 会读写部分和。数据分发使用 DMA 与可配置互连。这是论文采用的 GEMM 映射，不是对所有 XDNA 程序的限制。[论文 §3–4](https://arxiv.org/html/2512.13282v1#S4.SS2.SSS1)

### 4.2 Tile SRAM 怎样利用？会与其他 core 联动吗？

本地 SRAM 可以同时承担输入缓冲、C 部分和存储与数据布局转换的工作空间。例如输入采用双缓冲时：

```text
A/B buffer 0：当前批次，被本地 kernel 消费
A/B buffer 1：下一批次，由 DMA 填充
C buffer：跨全部 K 批次保留部分和
```

容量仍受 [[Tiling]] 中的约束：

$$
d_As_AB_MB_K+d_Bs_BB_KB_N+s_{\mathrm{acc}}B_MB_N
\le S_{\mathrm{local}}.
$$

C 留在 L1 时，core 内部可能反复读取、更新、写回 C；它减少的是跨更外层边界的部分和搬运。若 C 能留在寄存器或内部累加器，则还能减少更内层的流量，但需要足够的相应资源。

其他 core 可以使用相同 A/B 输入的副本，却维护不同的 C Tile。例如 core$(0,0)$ 与 core$(0,1)$ 共享 $A_{0,q}$ 的来源，但更新的是不同输出。片上广播共享了源端读取，不等于它们共享同一物理 L1 buffer。

在 M/N 分工下，不需要跨 core 合并同一个 C 的部分和；若改为让多个 core 分担同一输出的不同 K 段，就需要额外 reduction。这是另一种空间划分选择。

## 5. Broadcast 与 Systolic Forwarding 真正差在哪里？

为了公平比较，先保持每个计算位置的计算粒度不变，都负责一个矩阵 Tile。

**Block-systolic forwarding：** $A_{i,q}$ 从一侧进入，沿同一行的计算位置逐级转发；$B_{q,j}$ 沿列转发，各位置按数据到达顺序更新本地 C。这是可以设计的一种粗粒度 systolic 组织。

**Broadcast core array：** 上游网络直接向目标组分发 A/B；中间可以经过交换机或复制节点，但不要求经过前一个计算 core 的消费与软件转发流程。

| 比较点 | Systolic-style forwarding | Broadcast + independent core |
| --- | --- | --- |
| 复用机制 | 输入沿邻居链被多个位置使用 | 上游数据向多个目标分发 |
| 下一个位置依赖谁供数 | 邻居转发路径 | 分发网络与输入缓冲 |
| 计算时序 | 通常与规则传播波前关联 | 可由各 core 依据本地数据就绪执行 |
| 主要协调 | 传播、对齐、有效位与可能的流控 | DMA、buffer 使用权、队列与背压 |
| 部分和 | 可在本地驻留 | 同样可在本地驻留 |

广播不表示“瞬间送到所有地方”，也不保证目标同时收到。物理网络可以是树状、分层或多跳；相邻交换节点转发也不等于计算 core 在执行 systolic operand forwarding。

同样，systolic 不能被简单定义为“没有 SRAM”或“只算标量”。本文比较的是明确的数据路径，不能凭芯片外观上都是二维阵列就判定两者相同。

## 6. 标量 Systolic 的 Skew 与周期数

### 6.1 为什么输入需要错开？

回到 $R\times S$ 标量 output-stationary 阵列。采用以下理想时序：

- 行、列从 0 编号，第一个有效 MAC 所在周期编号为 0。
- A 向右、B 向下每周期走一格；每个 PE 每周期完成一次累加更新。
- A 的 $a_{ik}$ 在周期 $i+k$ 从第 i 行左边界注入；B 的 $b_{kj}$ 在周期 $j+k$ 从第 j 列上边界注入。
- 忽略额外的 MAC 流水线延迟、清零与输出读出成本；输入持续供给且无停顿。

A 到 PE$(i,j)$ 要横走 j 格，B 要竖走 i 格，两者相遇时间都是：

$$
\boxed{t(i,j,k)=i+j+k}.
$$

Skew 使具有相同 k 的操作数在正确位置相遇。它不是任意浪费周期，而是边界注入与内部传播相配合的时序安排。

### 6.2 一个 $2\times3$、$K=3$ 的时间表

| PE | 执行 $k=0$ 的周期 | 执行 $k=1$ 的周期 | 执行 $k=2$ 的周期 |
| --- | --- | --- | --- |
| (0,0) | 0 | 1 | 2 |
| (0,1) | 1 | 2 | 3 |
| (0,2) | 2 | 3 | 4 |
| (1,0) | 1 | 2 | 3 |
| (1,1) | 2 | 3 | 4 |
| (1,2) | 3 | 4 | 5 |

每个 PE 都做 3 次 MAC，但开始时刻不同。最后一次 MAC 在周期 5 执行，因此共经历 0–5 六个周期。

一般情况下，右下角最后一项的周期编号为：

$$
t_{\mathrm{last}}=(R-1)+(S-1)+(K-1)=R+S+K-3.
$$

周期编号从 0 开始，所以周期总数为：

$$
\boxed{N_{\mathrm{cyc,systolic}}=K+R+S-2}.
$$

这个公式描述上述模型从首次 MAC 到全阵列最后 MAC 完成的计算区间，不包括把全部输出搬走的时间。不能将它直接当成所有 systolic 设计的完整 kernel 延迟。

## 7. 换成直接广播，是不是一定更快？

> [!question] 如果直接把 A/B 喂给每个 PE，不等邻居传播，应该能用更少周期完成吧？

在一个强理想模型下，这个直觉成立：每周期 k 将 $a_{ik}$ 送给第 i 行所有 PE，将 $b_{kj}$ 送给第 j 列所有 PE，且没有额外分发延迟，则所有位置都在周期 k 计算对应的乘积：

$$
t_{\mathrm{broadcast}}(i,j,k)=k,
\qquad \boxed{N_{\mathrm{cyc,broadcast,ideal}}=K}.
$$

相对前面的单次 systolic 计算区间，少了 $R+S-2$ 个周期。

### 7.1 “时序和原来一样”需要修正

如果仍按原来的 $t=i+j+k$ 安排 MAC，即使数据提前到达，也未必提前完成。上述 K 周期结果同时改变了供数方式与执行时序：取消原有位置错位，让所有 PE 在同一个 k 周期更新。

| 阵列 | K | Systolic 周期数 | 理想广播周期数 | Systolic 平均 MAC 槽位利用率 |
| --- | --- | --- | --- | --- |
| $4\times4$ | 8 | 14 | 8 | $8/14\approx57.1\%$ |
| $4\times4$ | 64 | 70 | 64 | $64/70\approx91.4\%$ |
| $16\times16$ | 64 | 94 | 64 | $64/94\approx68.1\%$ |
| $16\times16$ | 1024 | 1054 | 1024 | $1024/1054\approx97.2\%$ |

每个 PE 仍需执行 K 次 MAC。被减少的是跨阵列传播导致的位置错位，不是每个输出所需的有效算术工作。

### 7.2 为什么理想广播不自动等于更好的硬件？

直接广播要求每个输入驱动整行或整列。大阵列会面临扇出、长导线、负载与时序问题，可能需要 repeater、流水级或分层网络。Systolic 使用规则的局部连接，但要承担传播波前。具体代价取决于实现。

每个逻辑 k 需要的不同输入数仍是 R 个 A 元素加 S 个 B 元素；两种方式都需要这些数据。Systolic 的注入在物理周期上有 skew，广播则在理想模型中同步供给。同样的不同元素数，不代表片上网络字节跳数、峰值供数模式或能耗相同。

比较墙钟时间还要考虑频率：

$$
T_{\mathrm{compute}}=\frac{N_{\mathrm{cycles}}}{f}.
$$

广播若减少周期却降低频率，实际时间未必缩短；网络自身也可能有启动与流水线延迟。长 K 时，$K/(K+R+S-2)$ 趋近 1，单次传播开销会被更多有效计算摊销。

### 7.3 单 Tile 延迟与连续吞吐要区分

前面的表只比较一个输出区域。连续执行多个区域时，要另看下一批能否与上一批重叠、C 是否有多份累加上下文、输出何时读走、输入缓冲是否足够。

不能将 $K+R+S-2$ 无条件乘以输出块数，也不能直接把单次延迟的减少当成同等比例的稳态吞吐提升。对于每周期一个 MAC 的 PE，K 次累加的有效工作仍然存在；流水线只能组织这些工作和其他阶段的时间关系。

## 8. 回到 Core Array：不能直接套 K 周期广播模型

标量理想广播在计算数据通路上直接为每个 MAC 供数；broadcast core array 则把矩阵块作为逻辑传输对象，由 core 内部的指令序列完成局部 GEMM。

一次广播 $4\times8$ 的 A Tile，不代表 32 个元素同一周期全部到达，也不代表 core 一个周期算完块乘。DMA 可以通过许多传输拍把块写入 L1，core 再按内部粒度消费。

因此这里有三个独立的粒度：

$$
\text{标量 MAC}\quad\longrightarrow\quad
\text{矩阵指令块}\quad\longrightarrow\quad
\text{Core GEMM Tile}.
$$

阵列外部按 Tile 分发，不能推出内部一定是直接广播、systolic 或任何固定形式。相应地，$B_K$ 不是 core kernel 的周期数，前面标量模型中的 $R,S$ 也不能只换成 core 行列数就照搬延迟公式。

### 8.1 从工作量到计算时间模型

如果需要估计整个 GEMM 的计算服务时间，可从工作量除以有效处理速率出发。假设共有 $P_{\mathrm{core}}$ 个同速 core，每核每周期峰值为 h 次 MAC，频率为 f：

$$
\Pi_{\mathrm{peak}}=2P_{\mathrm{core}}hf,\qquad
T_{\mathrm{comp}}\approx\frac{2MNK}{\eta\Pi_{\mathrm{peak}}}.
$$

$\eta$ 表示所定义统计范围内的有效计算效率，会受 Tile、指令调度、本地访存和负载分配等影响。这个式子是计量关系，不会自行预测 $\eta$；把它当作预测模型时，需要说明效率如何获得、已经包含哪些等待。

外层流量可用 [[Tiling]] 的统计，再以 $T_{\mathrm{mem}}\approx Q_{\mathrm{outer}}/BW_{\mathrm{effective}}$ 估计搬运服务时间。只有在计算与搬运能够充分重叠、且两种服务时间的定义没有重复计入等待时，才可用两者最大值作理想瓶颈估计；真实端到端时间还涉及依赖、启动、排空与缓冲约束。

这些速率公式与具体阵列逐周期时序是不同分析层级。前者便于汇总瓶颈，后者解释数据何时到达、哪个单元何时执行。

## 9. 两种组织可以组合：层次化阵列

例如将一个逻辑 $64\times64$ 的标量计算区域，组织为 $8\times8$ 个子阵列，每个子阵列内部为 $8\times8$ 个 PE：

```text
上层缓冲与分发网络
    ├─ 子阵列(0,0)：内部邻居转发与局部累加
    ├─ 子阵列(0,1)：内部邻居转发与局部累加
    └─ …
```

上层把所需 A/B 子块分发给不同子阵列，下层用 systolic 处理。也可以让每个矩阵 core 内含小阵列，再由 core 层提供 SRAM、DMA 与控制。

这是一个设计可能性，不是上述论文的具体实现复现。需要分别决定上下两层的分块、输入共享、缓冲与时序，不能把理想全阵列广播的 K 周期结论直接套上去。

## 10. 用四个问题检查自己是否理解

1. **谁负责哪个输出？** 是一个 PE 对一个标量，还是一个 core 对一个矩阵 Tile？
2. **K 怎样归约？** 每批处理多少，部分和跨哪些批次保留，是否需要跨计算位置 reduction？
3. **输入怎样到达？** 经邻居转发，还是由上游网络分发？一个符号表示标量、子块还是完整行带？
4. **比较的是什么指标？** 源端流量、目的端副本、单次计算延迟、稳态吞吐与端到端时间需要分别说明。

其中 $A_{i,q}$ 的第二个块索引、C 跨完整 K 的生命周期，以及“直接供数后也要改变执行时序”，正是讨论中几次追问最终澄清的关键。
